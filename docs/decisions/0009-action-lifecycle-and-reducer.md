## ADR-0009: Action lifecycle, reducer, and validation surface

**Status:** Accepted
**Date:** 2026-05-03

## Context

Sessions 1–6 built the engine's data substrate (types, CT, catalog, hooks, abilities, map, ruleset, setup). Session 7 lands the action loop: the unit of state transition. Every change to `GameState` from this point forward — player commits, system events, status ticks, future damage and reactions — flows through a single shape called `Action`, validated by one function, reduced by one branching reducer, committed by one wrapper.

The decisions in scope:

1. **Action shape: per-kind payload/outcome, or open envelopes.** Either pin each `type` to its specific `payload` and `outcome` shape via a discriminated union, or keep `payload: unknown` / `outcome: unknown` (the session-1 skeleton) and let each reducer cast.
2. **Proposed vs. logged actions.** A controller (UI, AI) describes *what* it wants to do; the engine fills in seq, seed, timestamp, chain bookkeeping at commit time. Either expose one `Action` shape and have controllers leave envelope fields empty, or split the type into `ProposedAction` (the input shape) and `Action` (the logged shape).
3. **Reducer split.** Either one big switch in `reduce.ts`, or per-kind reducer functions plus a thin dispatcher.
4. **Validation surface.** Pure `(state, action, catalog) → ValidationResult` separate from reduce, or merged into the reducer's prologue. UI needs to preview legality without committing — that argues for separation.
5. **Pre-resolution hook semantics.** `onActionAttempted` can `block`, `replace`, or leave alone. Either thread a value through every handler (modifyStatQuery-style) or short-circuit on the first non-`allowed` result.
6. **commitAction's failure modes.** Validation failure and hook block both prevent commit. Either return both as a unified `{ ok: false; reason }` shape, or distinguish the stage where the rejection happened.
7. **Chain-depth cap behavior.** When a reaction chain exceeds the ruleset cap, either drop silently with a warning, emit a `chain_truncated` system event, or throw.
8. **First Action class-pinning enforcement.** Either the reducer (refuses an EquipAbility action that would break the pin), `setActiveBucket` (refuses the change at the ability-equip level), or `validateLoadout` (reports the violation as one of its outputs). The session-5 handoff named the reducer; the session-7 implementation revises that.

## Decision

**Action shape: discriminated union with per-kind payload/outcome pairs.** Each `type` in the union (`'move'`, `'use_ability'`, `'wait'`, `'set_facing'`, `'turn_start'`, `'turn_end'`, `'charged_action_resolve'`, `'status_tick'`) is paired with its specific `payload` and `outcome` types. The universal envelope (`sequenceNumber`, `source`, `actorId?`, `timestamp`, `seed`, `chainDepth`, `isReaction`, `parentActionSeq?`) is intersected onto every variant via `ActionEnvelope`. A separate `ActionOutcome` union exists for places that need to enumerate every outcome shape without the envelope.

**ProposedAction is a separate type from Action.** Controllers describe what they want as a ProposedAction (no envelope; just `type`, `source`, `actorId?`, `payload`). The engine fills in the envelope at commit time. This keeps the controller surface simple — UI doesn't need to understand seq numbers or seeds — and ensures the engine is the single source of envelope truth.

**Reducer split: per-kind branches with a thin dispatcher.** Each kind has its own pure function in `engine/actions/reducers.ts` (`reduceMove`, `reduceUseAbility`, etc.). `engine/actions/reduce.ts` holds the single dispatcher that narrows by `action.type` and calls the matching branch. Per-kind functions are individually unit-testable; the dispatcher is a small thing that just routes. The cast through `ReduceResult<ActionOutcome>` in the dispatcher is the price of TypeScript not narrowing return types through a switch — the cast is local, narrow, and documented.

**Validation as a pure separate function.** `validateAction(state, action, catalog) → ValidationResult` is exposed alongside the reducer. UI calls it to grey out invalid options without proposing actions to the engine. The signature accepts both `ProposedAction` and `Action` so the same function validates pre-commit and during replay verification. Internally it dispatches per-kind to focused validation routines (universal invariants + contextual rules per the design doc's two-layer model).

**Pre-resolution hooks: short-circuit on first non-`allowed`.** `runOnActionAttempted` walks the actor's collected `onActionAttempted` handlers in tier order (Equipment → Class → Passive → Status, the ruleset's order). A handler that returns `{ kind: 'blocked', reason }` short-circuits the runner; later handlers don't fire. A handler returning `{ kind: 'replaced', with }` mutates the in-flight action and continues — subsequent handlers see the replacement. Threading replacements through the chain matches the modifyStatQuery pattern; short-circuiting on `blocked` matches the design intent that Stop / Silence are unconditional.

**commitAction reports the failure stage.** `CommitResult` is a discriminated union: `{ ok: true; newState; committed }` on success, `{ ok: false; stage: 'validation' | 'hook_blocked'; reason; rejected }` on rejection. UI knows whether the failure was a rule violation (validation) or a contextual block (hook) and can word its feedback accordingly.

**Chain-depth cap: throw.** Exceeding the ruleset's `chainTermination.chainDepthCap` is a programmer-error path — type-based suppression and per-unit-per-turn caps should make legitimate chains shorter than the cap. The throw surfaces real engine bugs early. The `chain_truncated` system event the design doc names is *future ergonomics* once content depth makes the cap reachable in normal play; today's safety-net cap stays loud.

**First Action class-pinning lives in `validateLoadout`.** Session-5's handoff suggested the reducer as the natural enforcement point, but the cleaner implementation is at the validator: `validateLoadout` already runs in three places (`equipPassive`, `setActiveBucket`, `createInitialState`) and adding a pin check there covers all of them with a single rule. The new violation kind is `'first_action_pin_violated'` with `expected` and `actual` fields. The reducer doesn't need a separate clause; if a future EquipAbility action ever ships, it goes through `setActiveBucket` (which calls `validateLoadout`) and the pin check fires automatically.

## Consequences

- **Adding a new action kind is one entry per layer.** Add a `type` discriminant + payload + outcome to `engine/types/action.ts`; add a reducer function in `engine/actions/reducers.ts`; wire it into the dispatcher in `engine/actions/reduce.ts`; add a `validateX` clause if non-trivial; add a `ProposedAction` discriminant. Every consumer that exhaustively matches on `action.type` lights up the new kind via TS exhaustiveness. The cost is more files than a single open-payload reducer; the gain is exhaustiveness wherever you switch on type.
- **Outcomes are fully typed at the use site.** Consumers reading `outcome.kind === 'move'` get `outcome.pathTaken` typed without casts. Replays that pull `action.outcome` from the log don't need to know the kind in advance.
- **`computeActionSpeed` and adjacent CT helpers got `catalog` parameter via session 6.** Session 7's reducer threads catalog through every reducer branch, so they can resolve the active ruleset without an awkward second arg. The pattern is consistent across the engine.
- **`ProposedAction` simplifies controllers.** The UI / AI builds a `{ type, source, actorId, payload }` object and hands it to `commitAction`. No envelope, no seed bookkeeping. The engine owns envelope construction.
- **`commitAction` is the only path that mutates the action log.** The reducer returns the outcome; the wrapper appends. This keeps the reducer testable in isolation (no log threading) and makes log-shape changes a single-file edit.
- **`onActionAttempted` becomes a real hook.** Earlier sessions left it as `{ args: { ... }; return: unknown }`. Session 7 refines to `args: { unit; action: ProposedAction }` and `return: ActionAttemptResult`. Status authors writing Stop / Silence / Berserk-flavored statuses get typed return helpers.
- **`onActionTargeted` similarly refined.** Returns `ReadonlyArray<ProposedAction>` — the reactions to enqueue. Session 7 ships the runner shape; session 8 wires it from the damage pipeline when Counter content lands.
- **Chain bookkeeping is real.** `parentActionSeq`, `chainDepth`, `isReaction` populate on each commit. Replays can reconstruct the parent-child tree of an attack-and-counter exchange. Reaction caps and depth caps both live on the ruleset and are read at commit time.
- **First Action pin-enforcement is automatic.** EMPTY_LOADOUT is no longer a valid loadout for any class with a `firstActionCommandSet` — which is every class. Tests that constructed units with EMPTY_LOADOUT and routed them through `createInitialState` or `setActiveBucket` now build pin-satisfying loadouts via the new `knightLoadout(...)` helper. Tests that go through `makeGameState` directly (bypassing validation) keep using EMPTY_LOADOUT.
- **TurnState got a real shape.** `turnState: CurrentTurn | null`. A unit's turn-in-progress lives on the state from `turn_start` to `turn_end`; in-between, `null`. Validation reads the active turn for budget gating; the reducer decrements/increments counters. Reactions count against `reactionsUsedThisTurn` per reactor unit.
- **`ASSUMED_TURN_CT_COST` ↔ `ctCosts.moveAndAct` symmetry held.** The reducer reads `ruleset.ctCosts.{moveOnly|actOnly|moveAndAct|wait}` based on consumed counters — same value the projection uses for fast-forward. No drift between projection and reducer.

## Alternatives considered

- **Open `payload: unknown` action shape.** Rejected. Type safety at use sites disappears; every reducer branch becomes a runtime cast. The session-1 skeleton was OK because the envelope was the only thing in scope; session 7 has 8 distinct payload shapes and growing.
- **One Action type used for both proposing and logging.** Rejected. Controllers don't know seq numbers, seeds, timestamps, or chain bookkeeping. Forcing them to construct `Action` would either (a) require null/placeholder fields they can't fill, or (b) make commitAction's "fill in the envelope" a mutate-the-input pattern.
- **One big reducer switch in a single function.** Rejected. Would push the file to 500+ lines as branches grow with damage / charged actions / reactions. Per-kind functions stay focused, individually testable, and trivially diff-reviewable.
- **Validation merged into the reducer.** Rejected. UI needs to preview legality without committing. A merged path either runs validation twice (once in UI, once in reducer) or the UI commits and rolls back, both worse than a separate pure function.
- **Threading a "current proposed action" value through `onActionAttempted` like modifyStatQuery.** Considered. Replacement-then-allow flows want the threading. But blocking is unconditional — you can't unblock once blocked. Mixing the two semantics in one threading model gets confusing. Short-circuit on `blocked` keeps the runner simple; replacement still mutates the threaded action so a Stop-then-Berserk stack would Stop, period.
- **`commitAction` returning a single failure shape without stage discrimination.** Rejected. UI wants to distinguish "your action is illegal" (UI bug; show generic error) from "your unit is Stopped" (game state; show contextual feedback). Two `stage` values cost almost nothing and clarify the surface.
- **Chain-depth cap drops silently with a console warning.** Rejected. Silent failures are CLAUDE.md ground rule territory; throwing makes engine bugs visible. The `chain_truncated` event is reserved for the day caps are reachable by content.
- **First Action pin-enforcement at the reducer level.** Rejected per session-5 handoff revision. The validator already has the necessary hooks (it's called from every loadout-changing path) and the reducer would duplicate the rule. The handoff's reasoning ("when EquipAbility lands as a player action, refuse changes") doesn't apply because EquipAbility doesn't exist as a v1 action — loadout edits happen between battles, not during.
- **Skipping the chargeTicks > 0 branch entirely (defer to session 8).** Considered. Today the reducer throws for chargeTicks > 0 with a comment; the throw is documented and tested. When the first charged-ability content ships, the branch lights up: create ChargedAction, apply Charging status, return outcome with `chargedActionId`.
- **Storing `consumed` on `turnState` vs. re-deriving from action log at turn_end.** Storage chosen. Re-derivation would walk the log filtering by parent actor for every turn_end; storage is one O(1) lookup. The action log is the source of truth for *what happened*; turnState is an in-flight summary.
